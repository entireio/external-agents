## Findings

**1. `hooks.go:289-306` (+ `command_runner.go:44`) — `fetchSession` write→read→delete round-trip is fully avoidable**
`ExportSession` already holds the exported blob in memory (`out`, command_runner.go:36) and writes it to `sessionRef + ".raw"`. `fetchSession` then reads that file back (`os.ReadFile(rawPath)`), decodes, re-encodes to JSONL, atomic-writes the real ref, and `os.Remove`s the scratch file. That's one extra full-transcript disk write, one full read, and a create+unlink of `.raw` per call — pure overhead, since the bytes never left the process.
- Cheaper: give `CommandRunner` a bytes-returning method (`ExportSession(ctx, id) ([]byte, error)`) and feed `out` straight into `decodeTranscript` → `encodeMessagesJSONL` → `atomicWriteFile`. Eliminates the scratch file entirely.
- Cost: per-`fetchSession` call, ~2× transcript-sized I/O + 2 extra syscalls. Low priority in practice — the method's own doc comment says it's "reserved" and not on the production path — but it is trivially avoidable and the interface is package-internal, so nothing external constrains the signature.

**2. `session_jsonl.go:26-33 (line 27)` — `encodeMessagesJSONL` allocates a throwaway `[]byte` per message**
`json.Marshal(messages[i])` allocates a fresh slice for every message, which is then copied into `buf`.
- Cheaper: `enc := json.NewEncoder(&amp;buf)` and `enc.Encode(&amp;messages[i])` in the loop. `Encode` writes directly into `buf` and appends the `\n` itself (identical bytes, same HTML-escaping default), so you drop the per-message intermediate allocation and the manual `WriteByte('\n')`.
- Cost: N allocations avoided per encode (N = message count), on every turn-end write and every `fetchSession`. Minor, but this is the encode hot path and the change is a net simplification.

**3. `session_jsonl.go:51-57` — speculative whole-blob unmarshal on every decode, including the common JSONL case**
`decodeTranscript` first does `json.Unmarshal(trimmed, &amp;blob)` before the JSONL scanner. For the now-standard multi-line JSONL layout this always fails (trailing `{` after the first object), but only after fully parsing the first message object — which the scanner then parses again. So the first message is decoded twice on every call.
- Cheaper: the blob path only exists for legacy/ingestion input. Both formats start with `{`, so first-byte can't discriminate cheaply, but you can decode with a streaming `json.Decoder`: read one token; if the top-level object has a `messages` key treat as blob, else rewind/scan as JSONL — avoiding the redundant re-parse. Given the modest size, this is a low-severity note, not a must-fix.
- Cost: one extra first-message parse per `decodeTranscript`, and `decodeTranscript` is called on nearly every hook (`ReadSession`, `GetTranscriptPosition`, `ExtractModifiedFiles`, `ExtractPrompts`, `ExtractSummary`, `CalculateTokens`, `latestModelFromSessionRef`, `ReadTranscript`).

**4. `transcript.go:167-179` — `GetTranscriptPosition` full-decodes the transcript just to count messages**
It runs `decodeTranscript` (unmarshal every message) and returns `len(messages)`. Since the on-disk format is exactly one message per line, the position equals the newline count — the new test `TestGetTranscriptPositionMatchesLineCount` asserts precisely that.
- Cheaper (with caveat): `bytes.Count(data, []byte{'\n'})` would give the same answer for adapter-written files without any JSON parsing. The caveat is the dual-format support — a pretty-printed legacy blob has many newlines, so a raw newline count is only safe once you've confirmed the JSONL layout. Because of that format ambiguity I'd rank this a minor note rather than a clear win; flag it only if the legacy-blob path can be assumed gone.
- Cost: full N-message JSON decode per get-transcript-position call (once per checkpoint) where a byte scan would do.

**5. `transcript.go:182-256` — `ExtractModifiedFiles` / `ExtractPrompts` / `CalculateTokens` decode the whole transcript, then discard `[0:offset]`**
Each decodes all N messages and then `messagesFromOffset(messages, offset)` throws away the first `offset`. Since `offset` is a line index into JSONL, the leading `offset` messages are parsed for nothing.
- Cheaper: skip `offset` newlines first (a `sliceFromLine`-style byte scan, which the test file already implements) and decode only the tail.
- Cost: wasted decode of `offset` messages per call, proportional to how deep into the session you are — grows per-turn over a long session. This is pre-existing structure the diff carried over rather than newly introduced; modest given it's an adapter invoked once per hook.

## Altitude review: kilo JSONL transcript change

**1. `session_jsonl.go:42` `decodeTranscript` dual-mode (blob + JSONL) — wrong altitude, conflates two contracts.**
One function answers two unrelated questions: "parse a native Kilo *export* blob" and "parse *our* on-disk JSONL." The blob branch is load-bearing in exactly one place — `hooks.go:~296` `fetchSession`, which exports to `sessionRef+".raw"` and feeds that native blob through `decodeTranscript`. Everywhere else the on-disk layout is *always* JSONL (both `writeSessionPayload` and `fetchSession` end by writing `encodeMessagesJSONL`). Folding the native-export reader into the on-disk reader makes the disk contract ambiguous: a reader can't tell from the signature whether it's handling ingested Kilo data or a checkpoint slice. Cleaner form (and what omp does — it never needs dual-mode because native == on-disk): a dedicated `parseKiloExport(raw) ([]SessionMessage, error)` used only at the ingestion boundary in `fetchSession`, and a `decodeTranscript` that understands JSONL and nothing else. The "legacy files still parse" justification is also worth pressure-testing — these are regenerated per-session scratch files under the Entire private dir; if no durable legacy blobs exist on disk, that half of the dual-mode is speculative back-compat.

**2. `transcript.go` `sessionIDFromMessages` / `startTimeFromMessages` — reconstructing session metadata from message payloads is the lower-altitude choice vs. omp's header line.** 
omp proves you can keep a session header *and* line-scope: the header is physical line 0, `parseSessionSlice` peeks the first line and tolerates its absence in a mid-session slice, and `parseFullSession` validates it. Kilo drops the header entirely and recovers identity from `msg.Info.SessionID` (first non-empty) and start time from the earliest `msg.Info.Time`, falling back to filename / `time.Now()`. This couples session identity to message-payload shape and silently loses real session start time (and any title) on scoped/compacted slices where no message carries `SessionID` (e.g. the `fourMessageTranscript` fixtures set none). The deeper form is to mirror omp: write one header record as line 1, report position as a physical line count, and track each message's physical line. That preserves session-level metadata as a first-class on-disk record instead of heuristically re-deriving it. This is the central altitude call — headerless is defensible *only* because kilo consumes almost no session-level metadata downstream, but the divergence from its sibling adapter (same repo, same JSONL problem, opposite decision) is a real maintainability smell worth a deliberate decision rather than drift.

**3. `session_jsonl.go:15-21` + `transcript.go` `messagesFromOffset`/`GetTranscriptPosition` — the "message index == line index" invariant is computed at the wrong layer and is actively undermined by the tolerant decoder.** 
`GetTranscriptPosition` returns `len(messages)` and `messagesFromOffset` slices `messages[offset:]`, i.e. kilo's offset unit is *surviving-message count*. But Entire's `SliceFromLine` and the encoder operate on *physical newline count*. These coincide only while every physical line is exactly one valid message — yet `decodeTranscript` deliberately **skips** blank and unparseable lines. So the same decoder that everything else routes through can make `len(messages)` &lt; newline count, at which point the position kilo reports and the byte offset Entire slices at refer to different boundaries. omp avoids this entirely by never collapsing the two counts: it records each entry's true physical `Line`, filters with `record.Line &lt;= offset`, and reports `session.Lines` (physical, including skipped/header lines). The invariant here lives in a doc comment and two tests rather than in the position abstraction. The robust shape is omp's — make physical line the offset unit so tolerance-driven line-skipping can't desync position from slicing.

**4. `hooks.go:507` `transcriptPath` — `.json` extension on JSONL content is mildly misleading, and kilo owns it.** 
The file is now newline-delimited JSON, not a JSON document; `.jsonl` would be honest. Kilo constructs this name itself (`safeSessionID(sessionID)+".json"`), so it's changeable. Low stakes and there's a small coupling — `ReadSession` derives the fallback id via `TrimSuffix(base, Ext(...))`, which is extension-agnostic so a rename is safe — but flag it as a minor correctness-of-naming nit, not urgent.

- **`atomicWriteFile` (`session_jsonl.go:86`)** — temp-file + rename is the correct depth and matches omp's `WriteSession`/`atomicWriteFile` pattern exactly. Good shared shape, applied consistently (`WriteSession`, `writeSessionPayload`, `fetchSession`).
- **`encodeMessagesJSONL` (`session_jsonl.go:24`)** — small, single-purpose, guarantees the trailing-newline-per-message on the write side. The encode side is the right place for that guarantee; the gap is only that the read/position side doesn't uphold the same invariant (finding 3).
- **`shellQuote`/`isSafeResumeRune` (`agent.go`)** — allowlist-based quoting of the resume command is at the right altitude; it's a self-contained hardening of a display/exec string, not a bandaid layered on shared infra. Unrelated to the JSONL change but correctly scoped.
- **`compact.go` adding `PartReasoning/PartFile/PartSubtask` no-op case** — explicitly enumerating and documenting the dropped part types (rather than a silent `default`) is the right depth; the comment about losing thinking signatures is the kind of contract note that belongs here.

**Net:** the JSONL direction is sound, but three things sit a layer too low relative to the omp sibling: the dual-mode decoder (split it), headerless metadata recovery (reconsider a header record), and offset-as-message-count vs. physical-line (adopt omp's physical-line model).
